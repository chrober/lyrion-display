# Lyrion Display v0.4.0 — startup performance and Fire TV compatibility

**Development/QA plan only. This document does not tag or publish v0.4.0.**
The main application remains at v0.3.0 / versionCode 9 until the
separate version-bump and Java 25 release-preparation work is approved.

## Supported devices (non-negotiable regression gates)

- **Amazon Fire TV Stick 4K (1st generation, 2018)** with Alexa Voice Remote,
  retail product ASIN **B07PW9VBK5**.
- Fire TV build model **AFTMM**, **Fire OS 6**, **Android 7.1 / API 25**.
- Preserve **minSdk 22** (Android 5.1); do not add APIs or dependencies that
  require Android 8+ or newer. Java 25 is an offline *build toolchain* for
  a future release, not a required Android runtime.
- Preserve `com.chrober.lmsmaterial.nowplaying`, the production signing
  certificate, saved server/player/settings, the Fire TV launcher icon,
  D-pad/Menu/Back remote behavior, and the view-only Now Playing contract.
- An AOSP API 25 emulator is useful for compatibility regression tests but
  **cannot validate Fire OS system WebView, launcher, remote or memory behavior**
  on the actual hardware.

Amazon's device specification:
https://developer.amazon.com/docs/device-specs/identify-fire-tv-devices.html

## First performance change: overlap guarded probe and WebView preparation

Before the change, `showDisplay()` waited for
`MaterialSkinProbe.check()` to return, then constructed/configured a WebView,
then requested the Now Playing page.

Now it starts the background probe and **prepares an empty, origin-restricted
WebView while the HTTP response is pending**. The native opaque loading screen
remains in front. Only the successful probe callback may call
`browser.loadUrl(activeUrl)`. If the probe fails, the renderer is disposed
before displaying the error dialog. A stale response is ignored using
`requestSerial` and the matching startup trace.

The change is deliberately conservative:
- no WebView navigation or playback request before Material Skin verification;
- no new AndroidX/WebKit dependency or runtime API requiring a newer Fire OS;
- no changes to retry policy, HTTP timeouts, WebView security settings,
  stored connection, remote controls or settings reuse;
- no renderer held in memory after an unsuccessful probe.

Expected benefit: overlap the native WebView initialization cost and existing
network preflight, especially when cold-starting on older Fire TV hardware.
**The performance gain is a hypothesis until measured on a real device.**
A fast network response or slow WebView initialization may produce little or
no improvement.

## Local startup measurements (no telemetry)

For each **new connection/cold start**, a single `LyrionStartup` log line
records durations in monotonic milliseconds:

| Field | Meaning |
| --- | --- |
| `outcome` | `ready` when Material's DOM/customizations are ready, or `error` |
| `total_ms` | Begin guarded connection to ready/error |
| `probe_ms` | Full HTTP Material Skin probe duration, retries included |
| `webview_prepare_ms` | Creating and configuring the empty WebView + overlay |
| `post_probe_ms` | Last probe response until ready/error |
| `navigation_to_ready_ms` | WebView loadUrl to Material Skin DOM ready |

A value of `-1` means the stage never occurred. No player ID, hostname, IP
or listening port is included, and no measurements leave the device.
The metrics do **not** start at process creation; they measure the guarded
connection path. Subsequent reuse of a verified WebView is intentionally not
reported as a cold start.

### Manual test on the Fire TV Stick 4K

On a development machine with Android Platform Tools installed (PowerShell):

```powershell
adb connect FIRE_TV_IP:5555
adb shell getprop ro.product.model
adb shell getprop ro.build.version.sdk
adb shell getprop ro.build.version.release
# Expected model AFTMM, SDK 25, Android 7.1.x.
adb shell am force-stop com.chrober.lmsmaterial.nowplaying
adb logcat -c
adb shell am start -W -n com.chrober.lmsmaterial.nowplaying/.MainActivity
# Once the full Now Playing display appears:
adb logcat -d -s LyrionStartup:I
```

First configure a reachable Lyrion server/player using native Settings.
Repeat the cold-start test **5–10 times**, ideally after warmup of the Fire TV
system WebView, keeping the server and Wi-Fi conditions similar. Compare the
median and spread of `total_ms`, `probe_ms` and
`webview_prepare_ms` across candidate builds. A high `total_ms` with a
low `probe_ms` suggests WebView/Material rendering; a high `probe_ms`
suggests network/server startup. `am start -W` measures Android Activity
startup and **is not equivalent** to Material Skin DOM ready.

To compare against v0.3.0, which did not emit these timing fields, use the
same external screen/video timing method for both versions or first build a
QA-only **baseline instrumentation** against the unchanged v0.3.0 source.
Do not claim millisecond improvements based on differing metrics.

### Fire TV acceptance checks before v0.4.0 release

- Install a production-signed candidate as an **in-place update** over
  v0.3.0; verify that existing preferences remain intact.
- Repeat cold starts with a running, slow-starting and unavailable server.
  The empty WebView must never display an unverified page or raw error.
- Test Settings → Now Playing reattachment (no unnecessary probe or reload).
- Verify Menu, D-pad, OK, Back, touch/gear animation, screen-awake behavior,
  cover/track transitions and working custom themes.
- Leave the display running for several hours; verify no renderer crash or
  increasing memory usage.
- Confirm original Fire TV launcher icon persists.
- Run API 25 and API 29 emulator smoke tests in GitHub CI, but record a
  **real AFTMM / Fire OS 6** smoke-test result separately.

## Future release boundaries

- The Java 25 toolchain and versionName/versionCode bump are separate work
  after the performance behavior and hardware compatibility are accepted.
- The existing disabled v0.3.0 F-Droid recipe remains pinned to Java 17 and
  its exact historical source SHA; **never retrofit Java 25 to that recipe**.
- No branch named `publish/v0.4.0`, no `v0.4.0` tag, signing action, GitHub
  Release or F-Droid submission is part of this performance PR.
