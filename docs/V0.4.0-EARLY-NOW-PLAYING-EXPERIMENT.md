# v0.4.0 — opt-in early Now Playing readiness A/B experiment

**QA only, unpublished, OFF by default.** Supports API 23+ (including the
original Fire TV Stick 4K / Fire OS 6 / API 25); minSdk 22 unchanged.

## Motivation from real hardware

Five cold starts: total startup median **3475 ms**, final page load
**2034 ms**, options callback **598 ms**, but actual options script
execution only **0.7 ms**. WebView commit sometimes arrives after
onPageFinished; simply using commit as readiness would be unsafe.

## How the experiment works

Settings → PERFORMANCE (EXPERIMENTAL) → **Early Now Playing readiness**.

- Existing trusted origin/server probe stays mandatory before navigation.
- On API23+ start of the **actual, trusted non-np-only page**, issue a
  bounded, read-only DOM check **only on a fresh, probed cold connection**.
  The redirect stub and reused WebViews are excluded to avoid evaluating
  scripts in an old document. No longer wait for onPageCommitVisible:
  physical Fire OS 6 traces showed it sometimes arrived after finish.
- Require two consecutive checks with the #app root, visible laid-out
  Now Playing controls and an ancestor Vue instance mounted.
- At most **20 checks**, 130 ms between attempts (but stop immediately at
  onPageFinished). A **550 ms watchdog** expires a missing JavaScript
  callback and invalidates its result before scheduling the next probe.
  This prevents the first pre-navigation evaluation from blocking later
  checks indefinitely. No JS bridge, resource interception, new network
  requests, metadata reads or player controls.
- Only after passing those checks run the existing display-options
  JavaScript and postVisualStateCallback, with the native overlay held
  until the existing completion callback.
- The original onPageFinished readiness path remains the fallback.
  If a speculative early options evaluation hangs, a 1.4-second
  watchdog resumes the normal path; stale evaluations are ignored.
- Disabling the checkbox restores the original behavior on next
  navigation/cold connection. API22 cannot enable this experiment.

Important: visible Vue controls do not guarantee album art or track
metadata finished loading. Check actual Fire TV output for blank content,
flicker, wrong player, new delays, and unexpected WebView crashes.

## Logcat

The existing LyrionStartup line retains total_ms and visual_state.
The native LyrionStartupDetail line adds:

- early_mode=off|on: selected experiment state
- early_probes: number of passive checks attempted
- early_replies: number of callbacks accepted from the current page
- early_timeouts: number of missing callbacks invalidated by the watchdog
- early_qualified_replies: count of individual fully qualifying DOM snapshots
- early_first_probe_ms / early_last_reply_ms: time from navigation start to
  first probe request / last accepted callback; -1 means unavailable
- early_last_app / early_last_controls / early_last_vue /
  early_last_visible: **0/1** readiness flags in the latest accepted probe,
  **-1** if no probe returned
- early_candidate_ms: elapsed from navigation to stable visible controls
  (-1 when not reached)
- ready_source=early|finished|none: whether the original JavaScript
  readiness completed before onPageFinished (or used its fallback)

Hardware evidence (22 November 2026): with the preceding implementation,
**ON reported 0 early successes across 10 launches** and nine had
**early_probes=0** (the tenth had just one). Medians were 3449.5 ms OFF
versus 3389 ms ON, without a proven change in actual start behavior.
This is **NOT** evidence of a 60 ms speedup; the first OFF block was
colder/slower and the second matched baseline. It identified the
late-commit trigger as a blocker. The new build changes **only the trigger,
bounded polling, and logging**; its performance is untested on hardware.

Use the same self-contained PowerShell `& { ... }` A/B script from the
previous session. Keep Pre-render hidden WebView OFF. Run
OFF → ON → OFF → ON, at least five cold launches per block; compare
median total_ms and successful callback/timeout rates. If ON starts
show early_probes but early_replies=0, the vendor WebView is deferring
JavaScript. If replies arrive but early_last_vue/visible=0, the DOM
gate is too strict or genuinely premature. If ready_source remains
finished in nearly every launch, the experiment is unlikely to help. **Do not interpret ready_source=early**
as proof of complete track/player contents or an actual speedup.

Useful success criterion: at least **200–300 ms reproducible median
improvement**, with no incomplete Now Playing UI or stability regressions.
This threshold is a test objective, not an expected result.

Do not publish v0.4.0, tag a release or submit F-Droid until hardware
acceptance. The signed candidate must be built with the existing production
certificate, reproducible and pass API22/25/29 Android instrumentation.
