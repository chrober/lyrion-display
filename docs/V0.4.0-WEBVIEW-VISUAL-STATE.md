# v0.4.0 — API 23 WebView visual-state QA, including Fire OS 6

The **Fire TV Stick 4K (2018, AFTMM, Fire OS 6 / Android API 25)** is a
supported target. Android **minSdk 22** stays unchanged. No new AndroidX
WebKit library or dependency was added. This is a QA-only code change:
**no tag, publication or F-Droid submission**.

## Two distinct features

### 1. Visual-state callback — on by default on Android API >= 23

Only after Material Skin returns the existing JavaScript "ready" response do
we post `WebView.postVisualStateCallback`. On callback, the wrapper:
- changes the WebView from INVISIBLE to VISIBLE if the experiment below is on;
- removes its native loading overlay;
- records a device-local startup metric.

The callback says that existing DOM updates are **eligible for the next
draw**; it does **not** mean that photons have reached the TV, that album art
arriving later has finished downloading, or that WebView's page is faster.

On API 22 the original JavaScript-ready behavior is used without calling
any API 23 methods. On API >= 23 a **1.5-second fallback** prevents stuck
loading screens when a vendor WebView never delivers the callback.
Timeouts are distinguished from successful visual callbacks in the log.
All callbacks and fallback timers are invalidated on new page navigation,
leaving the display, destruction or a connection failure. Old renderer
callbacks cannot reveal a new page.

### 2. Experimental off-screen preraster — OFF by default

Settings → **PERFORMANCE (EXPERIMENTAL)** →
**Pre-render hidden WebView**.

When enabled on Android API >= 23, the WebView is attached to the window
as INVISIBLE while loading, and `WebSettings.setOffscreenPreRaster(true)`
can raster it before it is revealed in `onComplete`. This feature **may use
extra RAM**, and may be ineffective on a particular Fire OS WebView.
On API 22 the option is disabled. Switching it off is always possible.
Changes to the experiment take effect on the next page navigation/cold
connection, not necessarily upon returning to an already verified display.

A successful experiment is not measured by a faster JavaScript-ready event
alone; look at total time to overlay removal and RAM/renderer stability.

Android references:
- https://developer.android.com/reference/android/webkit/WebView#postVisualStateCallback(long,android.webkit.WebView.VisualStateCallback)
- https://developer.android.com/reference/android/webkit/WebSettings#setOffscreenPreRaster(boolean)

## A/B test on actual Fire TV Stick

Keep the v0.4.0 **production-signed RC** over the installed v0.3.0. Do not
uninstall the app: its settings and signature are part of acceptance.
With ADB connected to the Fire TV:

```powershell
adb shell getprop ro.product.model
adb shell getprop ro.build.version.sdk
# Expect AFTMM and 25.

adb shell am force-stop com.chrober.lmsmaterial.nowplaying
adb logcat -c
adb shell am start -W -n com.chrober.lmsmaterial.nowplaying/.MainActivity
# Once the display is visible:
adb logcat -d -s LyrionStartup:I

# Capture memory with the display up:
adb shell dumpsys meminfo com.chrober.lmsmaterial.nowplaying
```

With **pre-render OFF**, perform 5–10 starts, recording `total_ms`,
`dom_to_visual_ms`, `visual_state` and `preraster=off`. Enable the setting,
repeat the same tests with `preraster=on` and similar Lyrion/Wi-Fi
conditions. Alternate ON/OFF sessions to reduce thermal/server/cache bias.
Observe memory, cover/track transitions, and long-running stability.

Example (illustrative, not a result from actual Fire TV hardware):
```text
LyrionStartup: outcome=ready total_ms=840 probe_ms=75 ...
  dom_to_visual_ms=22 visual_state=callback preraster=off
```

`visual_state=callback` means WebView reported its state ready for next draw.
`visual_state=timeout` means the 1.5-second safety fallback revealed it;
`visual_state=api22` means the API 22 JavaScript-only path was used.
Do not interpret a timeout as confirmed visual readiness.
`dom_to_visual_ms=-1` on an error means the visual stage did not complete.
Existing `navigation_to_ready_ms` now refers to **overlay removal**
rather than just JavaScript acknowledgment.

For native memory, `dumpsys meminfo` shows the app's heap and useful
process information, but WebView rendering can involve additional processes;
interpret values conservatively. Do not use apparent small median differences
as grounds for retaining a memory-intensive setting.

## Automated regression gates

- JVM tests: minSdk/API22 feature policy, API25 opt-in, startup timing
  semantics and fallback classification.
- API22 emulator: original JavaScript-ready fallback/no unsupported API calls.
- API25 emulator: Fire OS 6-level API availability and native visual callback.
- API29 emulator: modern Android regression coverage.

Android emulation **cannot prove** Fire OS's vendor WebView, Alexa Voice
Remote behavior, frame rate, or hardware memory characteristics. Leave the
experiment OFF unless real AFTMM measurements establish a clear advantage.
