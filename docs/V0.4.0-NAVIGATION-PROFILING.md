# v0.4.0 — investigate ~3-second Material Skin WebView navigation

**Diagnostics only, unpublished.** No change to Material Skin or Lyrion
server; no new network request, WebView security relaxation, analytics,
player-control command, remote-control behavior, or third-party dependency.

## Why more measurements?

On the physical Fire TV Stick 4K (2018, Fire OS 6 / API 25),
20 app-process cold launches yielded these medians:

| Setting | total_ms | navigation_to_ready_ms | dom_to_visual_ms |
| --- | ---: | ---: | ---: |
| Off (10 runs) | 3400 | 3104 | 174 |
| On (10 runs) | 3338 | 3052 | 180 |

This is **not** enough to conclude that offscreen preraster accelerates
startup: runs were sequential groups, the first off-run was an outlier
(3945 ms), and the measured difference was small.

The current source loads `/material/np-only`, which JavaScript-redirects
to the actual Material application. Then the wrapper evaluates its display
options, which **may trigger a full reload** if Material-origin localStorage
preferences differ. `dom_to_visual_ms` actually measures time **from the
wrapper's "ready" JavaScript acknowledgment** to the WebView visual callback,
not the browser's DOMContentLoaded event.

## Logging on Fire TV

Install a **new, production-signed unpublished RC with this commit** as an
in-place update; older v0.4.0 candidates cannot produce the new metrics.

```powershell
$adb = 'D:\Android\Sdk\platform-tools\adb.exe'
$device = '192.168.1.45:5555'
$package = 'com.chrober.lmsmaterial.nowplaying'
& $adb -s $device shell am force-stop $package
& $adb -s $device logcat -c
& $adb -s $device shell am start -W -n "$package/.MainActivity"
& $adb -s $device logcat -d -s 'LyrionStartup:I' 'LyrionStartupDetail:I' '*:S'
```

Each successful cold start should produce:
- **LyrionStartup**: unchanged overall, probe, preparation,
  navigation-to-visible and visual-state measurements.
- **LyrionStartupDetail phase=native**: main-frame transitions and time
  spent between WebView milestones, including the app's injected
  JavaScript customization evaluation/reload count.
- **LyrionStartupDetail phase=page_perf**: an asynchronous,
  **post-display** snapshot from the WebView Performance API. This
  evaluation does not hold up revealing the Now Playing display.

Typical output shape (illustration, **not hardware data**):

```text
LyrionStartup: outcome=ready total_ms=3380 ... preraster=off
LyrionStartupDetail: phase=native outcome=ready page_count=2 first_page_start_ms=...
LyrionStartupDetail: phase=page_perf state=ok nav_ttfb_ms=... script_count=...
```

## Native field definitions

| Field | What it actually means |
| --- | --- |
| `page_count` | Main-frame onPageStarted callbacks (not number of HTTP requests) |
| `first_page_start_ms` | Calling loadUrl to first onPageStarted |
| `np_stub_ms` | First started main-frame page to the np-only stub's onPageFinished, if observed; -1 if not observed |
| `final_page_start_ms` | loadUrl to **latest** non-np-only onPageStarted |
| `final_page_load_ms` | Latest non-stub onPageStarted to onPageFinished; **not** JavaScript application readiness |
| `final_load_to_ready_ms` | Latest onPageFinished to visual callback/timeout |
| `options_attempts` | Number of wrapper JavaScript customize/status checks |
| `options_last_eval_ms` | Duration from issuing latest evaluateJavascript to result callback |
| `options_reload_count` | Confirmed requests to reload due to wrapper-managed Material preferences |

Different page starts, reloads and callbacks may overlap and are not
necessarily additively decomposable. The last page is considered "final"
by its URL **path alone**, but no path/URL is logged.

## Page Performance API fields

All are integer milliseconds, counts, or 0/1 flags. **-1 means
unavailable or not completed**, not zero elapsed time.

| Field | Meaning |
| --- | --- |
| `nav_ttfb_ms` | Main-document requestStart to responseStart (network and cache effects possible) |
| `nav_download_ms` | Main-document responseStart to responseEnd |
| `dom_interactive_ms` | navigationStart to domInteractive |
| `dom_content_loaded_ms` | navigationStart to DOMContentLoaded-event end |
| `load_event_ms` | navigationStart to window load-event end |
| `resource_count` | Resource Timing entries available at sampling (not all requests) |
| `script_count`, `script_max_ms` | Count and longest single resource duration for initiatorType script |
| `style_count`, `style_max_ms` | Count and longest for initiatorType link/css |
| `image_count`, `image_max_ms` | Count and longest for initiatorType img |
| `data_count`, `data_max_ms` | Count and longest for fetch/xmlhttprequest |
| `other_count`, `other_max_ms` | Count and longest for remaining initiator types |
| `resources_last_end_ms` | Latest recorded responseEnd relative to page time origin |
| `app_present`, `np_controls_present` | Presence of relevant DOM elements, **not** proof Vue/player ready |
| `images_pending` | Count of `document.images` that are incomplete when sampled |

The `page_perf` metrics refer to the **current document**, typically
after np-only redirect and possibly another reload; they do **not** include
earlier documents. `resource_count` may underreport due to buffer size,
cache behavior, or cross-origin restrictions. Individual resource durations
overlap, so **never sum them as elapsed wall-clock time**.

This instrumentation **does not measure the LMS player WebSocket/long-poll
handshake** or identify server-side Material Skin JavaScript bottlenecks.
For that we would need explicit Material-Skin-provided application
milestones, or a separately scoped opt-in integration. We do not infer
connection readiness solely from presence of a DOM container.

## Second diagnostic pass — JS execution vs Android callback

Five **actual Fire TV Stick 4K** cold starts with preraster **off**
(22 November 2026) produced the following observations:

- `total_ms` median: **3408 ms**. Run 1 had unusually slow
  `probe_ms=1755`, whereas later probes were 283–303 ms.
- `page_count=2` every time, `options_attempts=1`,
  `options_reload_count=0`: no extra options reload in this sample.
- `final_page_load_ms` median: **1923 ms**.
- `options_last_eval_ms` median: **592 ms** (Android
  evaluateJavascript invocation to callback, *not* the JS execution time).
- `dom_to_visual_ms` median: **183 ms**. This is the wrapper's
  ready acknowledgment to next-draw callback, *not* DOMContentLoaded.

Two new read-only/diagnostic measurements address the outstanding ambiguity:

| New field | Meaning |
| --- | --- |
| `options_js_exec_us` | Actual time spent running the display-options JavaScript inside the renderer, measured with `performance.now()` in **microseconds**, -1 if unsupported |
| `options_callback_gap_ms` | Non-execution remainder of the Android evaluateJavascript wall-clock duration, approximately `options_last_eval_ms - options_js_exec_us/1000` — includes scheduling/IPC/callback delivery |
| `final_commit_ms` | loadUrl to latest actual page's `onPageCommitVisible` (API 23+, -1 on API 22) |
| `commit_to_finish_ms` | Actual page commit to `onPageFinished` |
| `commit_to_first_options_ms` | Commit until first options evaluation is issued |
| `commit_probe_callback_ms` | Commit until asynchronous *read-only* DOM snapshot callback |
| `commit_probe_after_finish` | 1 if that snapshot callback arrived after `onPageFinished`, 0 if before; -1 if unavailable |
| `commit_doc_state` | State observed **when the snapshot JavaScript executed**: 0 loading, 1 interactive, 2 complete; -1 unknown |
| `commit_app_present` / `commit_controls_present` | Whether `#app` / Now Playing controls existed at snapshot execution (0/1, -1 unknown) |

The commit snapshot uses a tiny read-only `evaluateJavascript` call.
**It does not apply display options or reveal the page early.**
The snapshot is delivered asynchronously, so it may run **after** page
finished. Such a result does not prove the DOM was ready at the moment
of commitment. Even `commit_app_present=1` cannot prove that Material's
player data, Vue component initialization, or cover art is ready.

The existing display-options script still executes exactly once per
attempt; a timing wrapper preserves its existing ready/reload/missing
states and applies no additional CSS or preferences. Timings are computed
using a single JS call so JavaScript execution time does not include
the Android main-thread callback delay.

### Repeat the measurement

Install the **new, production-signed v0.4.0 diagnostics candidate**, keep
preraster OFF, and run five process cold starts:

```powershell
& {
    $adb = 'D:\Android\Sdk\platform-tools\adb.exe'
    $device = '192.168.1.45:5555'
    $package = 'com.chrober.lmsmaterial.nowplaying'

    for ($run = 1; $run -le 5; $run++) {
        Write-Host "`n=== RUN $run / 5 ==="
        & $adb -s $device shell am force-stop $package
        & $adb -s $device logcat -c
        & $adb -s $device shell am start -W -n "$package/.MainActivity" | Out-Null
        for ($i = 0; $i -lt 50; $i++) {
            $lines = @(& $adb -s $device logcat -d -s 'LyrionStartup:I' 'LyrionStartupDetail:I' '*:S')
            if (@($lines | Where-Object { $_ -match 'phase=page_perf' }).Count -gt 0) { break }
            Start-Sleep -Milliseconds 500
        }
        $lines | Where-Object { $_ -match 'LyrionStartup(?:Detail)?: ' } |
            ForEach-Object { $_ -replace '^.*? I (LyrionStartup(?:Detail)?): ', '$1: ' }
        Start-Sleep -Seconds 2
    }
}
```

Look for `options_js_exec_us`, `options_callback_gap_ms`,
`commit_to_finish_ms`, and `commit_probe_after_finish` across several
starts. We can then decide whether starting the real display-options
script early is worthwhile **and safe** on the Fire OS vendor WebView.

Android's `onPageCommitVisible` (API 23) confirms that a new page has
committed for drawing; **it is not a Material Skin ready signal**:
https://developer.android.com/reference/android/webkit/WebViewClient#onPageCommitVisible(android.webkit.WebView,%20java.lang.String)

## Privacy and compatibility

The WebView JavaScript is read-only and only returns a fixed 20-element
numeric array. The Android app validates **every integer** against a
strict range before logging it under `LyrionStartupDetail`. We never log
resource names, page URLs, server IPs, player IDs, cover names, WebSocket
payloads, user metadata, or raw JavaScript errors.

Runs on the existing API 22+ WebView with ES5 JavaScript and unchanged
`minSdk 22`; instrumentation tests on API 22, 25 and 29, plus JVM
serialization/privacy and native-phase tests.

Once installed, gather at least **5 cold launches with preraster OFF**.
We first look at `page_count`, `options_reload_count`,
`final_page_load_ms`, `nav_ttfb_ms`,
`dom_content_loaded_ms`, `load_event_ms`, resource categories, and
`final_load_to_ready_ms`. Those numbers help decide whether the
next change should focus on the redirect, repeated loads, or resources.
